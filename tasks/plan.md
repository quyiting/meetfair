## 验证关卡

每任务运行计划中的定向测试；每模块运行 `npm test`、`git diff --check`，并对该模块改动的 JS 逐个运行 `node --check`。仓库无独立 build/lint 命令，不假称执行过。模板与样式用本机微信开发者工具编译，重点检查空房间、1 人、2 人、旧房间、未加入预览、已结束等状态。

所有模块接通后，在开发者工具逐项验证：

1. 建房选择 3 个候选日期、2 小时时长和预计人数；不填位置先分享的入口仍存在。
2. 一人先填写时间；不同日期分别有空／没空／未填，进度口径一致。
3. 在至少 2 人的受控数据下生成部分／全员可参加建议，确定新日期；旧搜索不能覆盖它。
4. 最终方案齐全后提交参加意向；改地点／时间后提示重新确认。
5. 地图选点提名、取消选点、刷新附近、投票、详情、最终选定；手动提名不丢。
6. 首页筛选；房主取消／确认结束；结束后只读但仍可退出、删除自身数据。
7. 再约一次只预填活动设置；取消不建房，确认后新房间从 0 成员开始，源房间不变。

不得改写现有真实聚会来完成验收。需要云端端到端时，先确认目标环境与带有“功能验收”名称、1 小时保留期限的测试数据范围，之后才部署／建测试房间。缺少第二个微信身份时，只报告已做的单身份 UI 和本地多身份事务测试，不声称双设备验收通过。

## 风险控制

- 旧 `availability` 的归属日期：换日期前固定到旧日期键，不迁移成新日期答复。
- 云数据库对象更新：涉及空对象转非空对象时沿用现有 `db.command.set(room)` 全对象替换方式，但必须先从事务读到的最新房间构造，避免覆盖并发写入。
- 多日期同开始时间：请求必须携带日期，单看 `meetingTime` 不足以判断搜索版本。
- 参加意向：客户端必须回传其看到的方案版本；服务端决定身份及当前版本。
- 提名与刷新：服务端独立存提名，刷新不接收客户端指定的整份提名列表。
- 结束房间：检查落在事务内，不能只在进入请求时读取一次。
- 再次组织：显式白名单，禁止 `Object.assign({}, oldRoom)` 复制房间。
